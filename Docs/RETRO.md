總共 7 個 commit，約 12 輪桌機截圖迭代，owner 手機實測 2 次，兩次都說太難。

## 哪裡做對了

1. **流體的截圖迭代迴圈。** 一個 `run.sh` 跑完整流程、按時間截圖，每輪 2 分鐘。沒有它流體不可能 5 輪就像拉花。這要保留並正式化（`tools/sim.sh`）。
2. **模型錯了就換模型。** 分層調了四輪參數不動，改推開場為 1/r 一次就分層。教訓寫進 CLAUDE.md §3。
3. **動作是資料、參數在 config。** owner 兩次修正都只動資料與 config，沒重寫程式。
4. **部署通路對。** Artifact 不能用陀螺儀，一開始就查清楚改走 Pages，推完 60 秒上線。
5. **模擬手持。** 最後加的 `?hand=1&play=1` 是唯一能在桌機上講「難度」的根據。應該第一天就有。

## 哪裡做錯了

1. **核心幻想沒先對齊。** 我照字面做「鋼杯左右擺、杯子跟著走」，owner 腦中是「鋼杯不動、杯子不穩」。這是一句話就能對的事，卻花了一整輪。**之後任何核心玩法先用 10 秒的 ASCII/文字情境跟 owner 對一次，寫進 DECISIONS 再動手。**
2. **把桌機模擬當成手感。** 兩次「太難」都是因為我在桌機上調、沒有手的雜訊、沒有自動轉向、沒有舊快取。手感只能在手機上判斷，而我沒有任何手機數據回來。**缺的是：手機端匯出數據、桌機重播。**
3. **owner 不知道玩的是哪一版。** 第二次回報「還是太難」時，新版才剛部署 60 秒。畫面上沒有版本號，我也沒在回覆裡寫「等到看到 vX 再玩」。
4. **沒有驗收清單、沒有狀態檔、沒有決策紀錄。** owner 的兩次修正只活在對話裡，README 混了說明、教訓、疑慮。新 session 進來會重讀一切。
5. **用 Python 字串替換改程式。** 一次造成 `const k` 重複宣告（整個模組載不起來，截圖全是首頁才發現），一次 assert 失敗讓 README 改了一半。改程式要用精確的 Edit，改完 parse check。
6. **一次塞太多改動再部署。** 10-09 一個 commit 同時改了推開模型、飄移、甜蜜點、平滑，owner 感覺變了也說不出是哪一個。
7. **甜蜜點為了裝下圖案越開越大**，縱向幾乎整杯，和 owner「偏上一小塊」的想像漸行漸遠，我只在 README 註記，沒當成決策提出來問。

## 和 Kaiju 工具包的對照：哪些值得搬過來

| 工具包做法 | 對我們的價值 | 採用 |
|---|---|---|
| TASK（WHAT）/ CLAUDE（HOW）分開 | 高：owner 的修正有地方落 | 採用（本次） |
| STATE.md 整份重寫、TODO 有 ID、DECISIONS 只增 | 高：換 session 不重讀 | 採用 |
| ACCEPTANCE.json 帶證據 | 高：「過了」要有截圖或數據 | 採用（16 項） |
| Reviewer 車道，不自己評分 | 中：圖案美醜交給新 context 對照真實拉花照 | 採用，需要 owner 給幾張參考照 |
| SessionStart hook 印狀態 | 中：便宜、省重讀 | 之後做，先用手動讀 STATE |
| Stop hook 不准停、30 小時時鐘 | 低：我們是 owner 在迴圈裡的短迭代，不是無人長跑 | 不採用 |
| 付費生成的 ledger、預算上限 | 現在無；之後背景、造型要生圖時採用，owner 已有 fal 流程與偏好 | 之後 |
| 桌面縮時、story camera | 中：`tools/sim.sh` 的截圖就是我們的 story camera，留檔到 `Docs/progress/` | 採用簡化版 |
| 「隨時可玩」每個 commit | 高 | 採用：每個 commit 要過 `tools/sim.sh auto` |
| token 衛生：一次阻塞等待、不貼 log | 中 | 採用 |

## 三條最重要的教訓

1. 手感只有手機算數；桌機只做回歸。沒有手機數據回流，就不要調手感。
2. 一次一個改動、帶版本號部署、回覆寫「看到 vX 再玩」。
3. 核心玩法先用一句話對齊，寫進 DECISIONS，再寫程式。
